# Maintenance and release policy

## Repository roles

- [`HerbertGao/pi-extensions`](https://github.com/HerbertGao/pi-extensions) is the independent source and release monorepo.
- [`HerbertGao/tifandotme-pi-extensions`](https://github.com/HerbertGao/tifandotme-pi-extensions) remains the GitHub fork used for Tifan upstream contributions.
- Sibling working repositories are upstream work areas, not package-manager workspaces. Never mutate a dirty sibling while importing it.

`upstreams.json` records repository review cursors, original-name companion repositories, and PyPI pins. `scripts/check-upstreams.mjs` validates these records, checks npm latest versions, pinned PyPI versions, and GitHub default-branch commits, and powers the daily `Upstream Monitor` workflow. `x-upstream.reviewedVersion` records an audited release that was deliberately not imported, so the monitor can distinguish a known product decision from a new release without falsifying imported provenance. For npm and PyPI release changes, the workflow updates the open upstream-tracking Issue with the matching title, or creates a new Issue when no matching open Issue exists. Unreleased commits remain visible in the workflow summary without opening an Issue. Query errors fail the workflow; without an independently detected release, they leave the Issue state unchanged.

### What the monitor reports

Imported forks and companions are not all reviewed from GitHub commits.

- If the upstream publishes to npm, monitor that npm version only. Do not import or flag unpublished GitHub commits. `pi-cc-extensions`, `pi-subagents`, `impeccable`, Tifan packages, and `pi-antigravity` are in this group. Their `upstreams.json` entries use `"watch": "npm"`.
- If the upstream publishes to PyPI and this repository pins it, monitor that PyPI version only. `graphifyy` is registered under `pypi` with `"watch": "pypi"`. The expected version is the requirement in [`pins/graphifyy`](../pins/graphifyy). A different PyPI version is a release update on the same upstream-tracking Issue. GitHub commits for that repository are not monitored, and the package stays out of the npm aggregate. Install and bootstrap steps are in [`docs/graphify.md`](graphify.md).
- If the upstream does not publish to npm but publishes GitHub releases or tags, monitor that release or tag. No current source uses this channel, so the monitor does not fetch releases yet.
- If the upstream publishes neither, review GitHub source commits. `NVlabs/SoL-Pi` is the current case and uses `"watch": "commits"`.

### Upstream Issues

`Upstream Monitor` only checks upstreams and syncs the tracking Issue with `scripts/check-upstreams.mjs --sync-issue`. It does not start an upgrade workflow. There is no dispatch flag, credential gate, or acknowledgement step to turn one back on.

Reviewed Upstream Upgrade CI is retired. Cursor cloud agents and the Grok Bot routine apply upstream-monitor Issues to pull requests. That work is outside this repository's GitHub Actions.

The former workflows are kept for source history under [`.github/workflows-disabled/reviewed-upstream-upgrade/`](../.github/workflows-disabled/reviewed-upstream-upgrade/README.md):

- `upstream-upgrade.md` and `upstream-upgrade.lock.yml` — Copilot engine, previously the active workflow
- `upstream-upgrade-agy.md` and `upstream-upgrade-agy.lock.yml` — earlier Agy engine copy (Antigravity CLI v1.3.6)

GitHub Actions loads only workflow files directly under `.github/workflows/`. Files in `workflows-disabled/` are not workflows, so a schedule, `workflow_dispatch`, or `gh workflow run` cannot start them. Do not move or recompile them back into `.github/workflows/`.

`COPILOT_GITHUB_TOKEN`, `GH_AW_CI_TRIGGER_TOKEN`, and `GEMINI_API_KEY` are not required for Upstream Monitor. Engine history for the retired workflows is in the archive README.

When applying an upstream Issue, versioned npm and GitHub companions bump by published version. Imported forks with local patches (`pi-cc-extensions`, `sol-pi`) use a full upstream-tree replay of local adaptations onto the latest in-scope upstream, not a selective file port. The resulting pull request runs `bun run check` and does not merge, publish, release, or tag.

Older Issues may still end with `<!-- upstream-agent-dispatched:<sha256> -->` from a successful in-repo dispatch. `scripts/check-upstreams.mjs` still skips rewriting an open tracking Issue when the report is unchanged and that marker matches. The monitor no longer writes the marker. Unacknowledged findings continue to refresh the Issue body on later runs, which is the same Issue-sync behavior as the paused dispatcher.

### Direct Tifan package migration

The aggregate pins and bundles five original Tifan packages directly: copy-response `0.2.6`, handoff `2.2.1`, Mermaid Open `0.2.0`, Recap `0.4.6`, and Rename `0.6.0`.

Normalized package comparisons established that copy-response and Mermaid Open are source-identical; Recap and Rename catch malformed config at their outer initialization boundary; and Handoff intentionally depends on Rename for generated session names. Handoff and Rename therefore move together, while the aggregate continues to provide `typebox`, which Handoff imports at runtime. Rename's malformed Herdr response produces the upstream warning during an explicit rename instead of being treated as unavailable; session naming still succeeds, and startup recovery remains quiet.

All Tifan-derived local package sources are removed without compatibility wrappers. Issue #131 removes the last one, `pi-stash`: bundled `pi-btw` already preserves the main editor draft while handling side questions outside the main conversation, so maintaining a Fork solely for `Alt+S` is not justified. Issue #134 also removes deprecated `@tifan/pi-titlebar-spinner`: its 1.x line retargets Herdr tab labels and can overwrite Rename's session-owned label, so the aggregate keeps Rename as the single tab-naming owner. Prior `@herbertgao/*` npm releases remain available but outside this repository's maintained package set.

### pi-cc-extensions 0.9.9 direct upstream migration

The local fork is retired: the complete upstream v0.9.9 source and test suite are imported at `17d294b` and republished as `@herbertgao/pi-cc-extensions`, keeping upstream's MIT license and attribution. The decision followed a full evaluation that ran every local-only and locally-modified regression test against the imported tree; upstream already covers most of the fork's fixes (width-adaptive summaries, POSIX paths, write-ownership yield, working-message stale-ctx, group viewport, shiki ordering, packaging, fullscreen isolation).

Nine fixes the evaluation confirmed missing are re-applied on top, each with its regression test: session-reference guards across session replacement (the former local PR #194), agent discovery reading `$PI_CODING_AGENT_DIR/agents` with unreadable entries skipped, Markdown fenced-block/inline-code protection for prose transforms, write-abort honesty after the file is written with real UTF-8 byte counts, diff `\r` splitting and colon-form SGR background stripping, native assistant-prototype restore and config-callback disconnect on reload, working-message `turn_end` and error-usage guards, agent-summary `file_path` fallback for empty `path`, and grouped-title hint preservation: at narrow viewports the collapsed-group line yields the tool-name list and then the counters before the trailing `click to show more` hint, which `collapsedHintHitbox` requires at end-of-line for the group to stay clickable.

Product decisions: compact mode shows upstream's full collapsed diff card; tool summaries use upstream's width-adaptive `toolViewportWidth` (80%, capped 24-column right margin); legacy bare `@session:<id>` references follow upstream's removal; the footer moves from the bundled `pi-footer` companion to pi-cc's built-in configurable footer, and `pi-footer` plus its promoted `chalk` dependency are removed from the aggregate.

Test harness: the package `test` script now runs through `scripts/test.mjs`, which sets `FORCE_COLOR=0` — upstream's write-collapsed assertions otherwise fail on terminals advertising color such as `COLORTERM=truecolor` while CI, without it, passes — and points `PI_CODING_AGENT_DIR` at a temp directory, because upstream tests otherwise persist a default config into the real `~/.pi/agent`. Upstream's own suite passes 272/272 in this environment; upstream's strict `tsc --noEmit` typecheck replaces the previous lenient wrapper script.

Deferred, with upstream PR candidates recorded above: MCP detection from tool descriptions (upstream detects MCP tools by name only), message-display native-background restore on mode off, and legacy `{ "enabled": false }` config normalization. Verification that closed the remaining evaluation questions: the real-PTY smoke (full theme/width matrix plus reinstall and reload cases) passes on the migrated tree. Upstream's compact-mode tail-line model renders the round summary (`Ran for …`) correctly after resume — the evaluation's two deleted upstream tests were re-ported asserting at transcript-container level, independent of the tail/anchor mounting model, and the smoke probe now recognizes compact round-tail hosts via the `pi.ccstyle.compact-assistant-toggle-round` symbol instead of treating them as a product regression. ## Package manifest standard

Every publishable package must have:

- `@herbertgao/<original-unscoped-name>` identity;
- explicit `license`, `files`, `repository.directory`, `homepage`, and `bugs`;
- `publishConfig.access = public` and `publishConfig.provenance = true`;
- a Pi resource manifest;
- `x-upstream` provenance for derived packages, or `x-origin: original` for packages authored in this repository;
- original copyright and license notices.

Cross-package dependencies use `@herbertgao/*`. The aggregate package pins exact versions and lists every maintained child and upstream companion in `bundledDependencies` so Pi can load resources through `node_modules/` under one isolated package root.

Maintained child packages use SemVer. A package with `x-upstream.trackVersion` follows its imported `x-upstream.version`, not the registry's newer unimported release. The version script publishes it as `<upstream>-local.N`: the first release on that import is `local.1`, and another local release on the same import increments `N`. The suffix is older than the upstream release, so it does not take upstream's next number. `changeset publish --tag latest` is required because npm otherwise does not point `latest` at a prerelease. Do not publish the bare upstream version for a tracked package; a later local release could not move forward without becoming newer than upstream. The aggregate package uses UTC CalVer in `YYYY.M.PATCH` form, without a leading `v` or a zero-padded month. Release PRs prepared in the same month increment `PATCH`; the first release PR prepared in a new month resets it to `0`. Add a patch Changeset for aggregate changes. `scripts/version-packages.mjs` runs Changesets, then normalizes the aggregate version for the UTC month when the version PR is generated and updates its generated changelog heading.

Recommended configuration files may be shipped under `packages/pi-extensions/examples/`, but package installation must not write into `~/.pi` or replace existing user configuration. Keep examples valid against the pinned companion version and assert their presence and parsing in the aggregate smoke test.

`packages/pi-extensions` uses `scripts/aggregate-bundle.mjs` during `npm pack` and `npm publish`. It bundles only the 25 direct Pi packages, then promotes their immediate runtime dependencies into the aggregate manifest so npm installs platform-specific transitive dependencies on the consumer machine. Do not replace this with Bun workspace symlinks or recursively bundled native dependencies. `bun run test:aggregate` must pass before release.

## CI and release validation

PRs run `.github/workflows/ci.yml`; pushes to `master` run `.github/workflows/release.yml`. Both call the read-only `checks.yml` workflow, which runs static checks, unit tests, and metadata validation in one matrix runner and aggregate packaging/integration tests in another. Together they cover every command in the local `bun run check`, which remains unchanged. Aggregate smoke failures still upload diagnostics.

Both callers retain a final job named `check` for required status checks. It succeeds only when the shared validation succeeds; failed, cancelled, or skipped validation cannot pass the gate. Do not rename this job without checking branch protection requirements. `NPM_RELEASE_ENABLED` gates only the release job, not validation on `master`.

The release job waits for `check` and alone receives write permissions and OIDC access. Keep publishing in `release.yml` so npm Trusted Publishing identity remains unchanged. Release runs remain serialized per branch, and published versions are still verified against npm after publishing.

### New scoped package release gate

A feature PR that introduces a new `@herbertgao/*` package may merge first, but **do not merge its Changesets “Version Packages” PR** until the new package has completed this one-time npm bootstrap:

1. Confirm `npm view @herbertgao/<package> version` still returns 404; this proves it is a genuinely new npm package rather than an ordinary release.
2. Publish the package's current version manually and publicly.
3. Configure npm Trusted Publishing for `.github/workflows/release.yml`.
4. Confirm `npm view @herbertgao/<package> version` returns the exact local version.
5. Only then merge the Version Packages PR and let the Release workflow publish the aggregate.

```bash
cd packages/<package>
npm publish --access public --provenance=false
npm trust github @herbertgao/<package> \
  --repository HerbertGao/pi-extensions \
  --file release.yml \
  --allow-publish \
  --yes
npm view @herbertgao/<package> version
```

Both `npm publish` and `npm trust` may stop with `EOTP` and print a browser authorization URL. Open that URL, complete the challenge, and wait for or rerun the command until it exits with status 0. Preliminary output such as `Publishing to ...` or `Establishing trust ...` is not success. Verify publication with `npm view`; treat Trusted Publishing as incomplete unless the `npm trust` command itself exits successfully.

**Do not treat a successful aggregate pack, install, or partial publish as proof that the child exists on npm.** `scripts/aggregate-bundle.mjs` embeds workspace child tarballs inside `@herbertgao/pi-extensions`, so the aggregate can publish and install successfully while the standalone child still returns npm 404. Changesets then reports the overall Release run as failed even if the aggregate itself was published. This happened when `@herbertgao/pi-extensions@2026.8.15` published but first-time `@herbertgao/pi-bark@0.1.0` failed with `ENEEDAUTH`.

If that partial-publish state occurs, the release job's `Verify published package versions` step identifies every local public package version still missing from npm. The recovery owner is HerbertGao: bootstrap the missing child at the version already present in `master`, verify it with `npm view` (or `node scripts/verify-published-packages.mjs`), then rerun the failed Release workflow. Do not bump or republish the aggregate solely to recover the missing child.

Run the aggregate package last, after all exact child versions exist. Do not create a long-lived `NPM_TOKEN` or a granular token that bypasses 2FA; the release workflow authenticates with GitHub OIDC and publishes with provenance. Enable the repository variable only after every package trusts the workflow:

```bash
gh variable set NPM_RELEASE_ENABLED --repo HerbertGao/pi-extensions --body true
```

The release workflow intentionally runs only on pushes to `master`. Do not add unrestricted `workflow_dispatch`: npm trusts the workflow file, and a manual run could otherwise select an arbitrary branch. If manual releases become necessary, first bind npm trust to a GitHub environment whose deployment branches are restricted to `master`.

Subsequent releases are Changeset PRs published through GitHub Actions OIDC with provenance. Never store an npm token in repository secrets.
